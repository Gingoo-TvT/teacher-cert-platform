# 第二次部署发布手册（`dfdfb91` → 当前候选）

> 本手册只用于准备和执行第二次停机发布，不构成发布 `GO`。发布准备 R1 fingerprint
> `bb3a31dc...925f88` 的正式独立结论为 `CHANGES_REQUESTED（0C/0H/4M/0L）`，不得物化为 carrier。
> 本轮整改会形成新的候选字节；必须重新生成 manifest、物化
> carrier，并取得同候选 Hosted 与项目级发布复核结论。未经用户另行明确授权，不执行 push、merge、
> 目标机停服、迁移、启动或切流。

- 第一次稳定应用版本：commit `dfdfb9199215d856b70abb653cb65b6f9ed46282`，镜像 tag `dfdfb91`。

## 2. 发布候选与离线包合同

所有字节稳定后，按以下顺序冻结发布身份：

1. 在仓库外 capture 并立即 verify 完整 dirty-worktree manifest。
2. 将 manifest 对应字节原样物化为 carrier commit；若物化后字节变化，废弃该 manifest 并重做。
3. 使用 carrier 完整 SHA 派生不可变 `APP_IMAGE_TAG=sha-<40位SHA>`。
4. 对该 carrier 新跑 Hosted workflow，不复用任何历史 run。至少归档 4/4 jobs、WS-8 六套
   46/46、WS-7 与 V33 合同、双镜像、双 SPDX、镜像/source revision 身份和 artifact 校验结果。
5. 独立复核确认 Hosted 证据与 manifest/carrier 是同一候选；提交方不得自签发布 PASS。

离线发布包至少包含：

- `docker-compose.yml`、`deploy/compose.cpu-v1.yml`、`deploy/compose.existing-volumes.yml`、
  `deploy/mysql-init/01-app-user.sh`；
- `deploy/rollback/dfdfb91/compose.yml`、同目录 CPU-v1 覆盖层与 MySQL init 文件；这些是首版端口与
  健康合同，禁止用当前 Compose 只替换旧 tag 来冒充回退；
- backend、frontend、MySQL 8.0.36、Redis、CPU-v1 MinIO 五幅镜像的离线归档；
- **另行保留首版五幅镜像**（backend/frontend `dfdfb91`、MySQL 8.0.36、Redis 7.4、CPU-v1 MinIO）
  的五个归档、local tag 与完整 image ID 清单；当前仓库不包含这些大归档，不得把“包结构已规定”写成
  “回退镜像已具备”；
- 非秘密环境变量增量模板，不含 `.env`、证件加密密钥、HMAC pepper、JWT、数据库、Redis、
  MinIO 或管理员凭据；
- candidate manifest、carrier SHA、每幅镜像 tag/ID/source revision、双 SPDX；
- 根与每个嵌套证据目录的 `SHA256SUMS`。每份清单必须精确覆盖其作用域内除自身外的所有普通文件；
  根清单还必须列出嵌套 `SHA256SUMS`，不得漏列子清单或容许额外文件。

目标机只允许先 `docker load` 并核对镜像 ID，再以 `--no-build --pull never` 使用预载镜像。包内不得
携带可移动 `latest` 标签。新 Redis 归档制作时，先把根 Compose 锁定的 digest 对应 image ID 另打
`teacher-cert-platform/redis-offline:sha-<carrier SHA>` 本地 tag，再对该 tag 执行 `docker save`；身份清单必须同时
记录源 digest、local tag 与 image ID，三者不一致即拒绝打包。

### 2.1 首版回退镜像归档

在首版目标仍健康且进入停机步骤之前，由获授权操作者从**预检已核验的五个目标容器**生成全新目录；不能拿
本机相似 tag 或历史聊天中的 ID 代替目标事实。下列命令只读取容器/镜像并写归档，不会停服：

```bash
rollback_images='<新的空目录>/rollback-dfdfb91-images'
mkdir -p "$rollback_images"
: >"$rollback_images/image-identities.tsv"
for item in \
  'mysql|teacher-cert-mysql-prod|mysql.tar' \
  'redis|teacher-cert-redis-prod|redis.tar' \
  'minio|teacher-cert-minio-prod|minio.tar' \
  'backend|teacher-cert-backend-prod|backend.tar' \
  'frontend|teacher-cert-frontend-prod|frontend.tar'; do
  IFS='|' read -r service container archive <<EOF
$item
EOF
  ref="$(docker inspect --format '{{.Config.Image}}' "$container")"
  id="$(docker inspect --format '{{.Image}}' "$container")"
  test "$(docker image inspect --format '{{.Id}}' "$ref")" = "$id"
  docker save --output "$rollback_images/$archive" "$ref"
  printf '%s\t%s\t%s\t%s\n' "$service" "$ref" "$id" "$archive" \
    >>"$rollback_images/image-identities.tsv"
done
(
  cd "$rollback_images"
  sha256sum backend.tar frontend.tar image-identities.tsv minio.tar mysql.tar redis.tar >SHA256SUMS
  sha256sum --check SHA256SUMS
)
```

五个 `docker load` 后必须逐行用 `docker image inspect <ref> --format '{{.Id}}'` 与第三列精确比较，再允许
`--pull never`。`deploy/rollback/dfdfb91/SHA256SUMS` 单独证明三份首版源资产；镜像目录的清单证明五个大归档，
两份清单都要被离线包根 `SHA256SUMS` 列出。

## 5. 正式停机升级顺序

以下仅在项目级发布复核 PASS 且用户明确授权部署后执行。升级和首版回退都必须固定原 project，并叠加
`deploy/compose.existing-volumes.yml`，把预检确认的四个原卷声明为 external；只复用 `-p` 不能证明会复用
首版显式卷。

```bash
new_dc='docker compose --env-file .env -p <首次部署实际project> -f docker-compose.yml -f deploy/compose.cpu-v1.yml -f deploy/compose.existing-volumes.yml'
old_dc='docker compose --env-file .env -p <首次部署实际project> -f deploy/rollback/dfdfb91/compose.yml -f deploy/rollback/dfdfb91/compose.cpu-v1.yml -f deploy/compose.existing-volumes.yml'
```

二者仅是下文阅读简写；实际执行时由操作者展开并再次核对目标，不能直接复制含尖括号的占位符。

`SECOND_RELEASE_ORDER: FREEZE_WRITES > CLOSE_PUBLIC_ENTRY > STOP_ALL_OLD > BACKUP_V32 > MIGRATE_V33_V35 > VERIFY > OPEN_TRAFFIC`

1. 冻结全部业务写入，确认没有进行中的导入、证书签发、视频定稿、备份或清理任务。
2. 先让外层 ingress（若有）进入固定维护状态，再用首版 Compose **先停止 frontend**；确认旧 frontend
   `.State.Running=false`，并从独立客户端同时验证正式域名根路径与同源 `/api/health` 只能连接拒绝或返回固定
   维护响应，不能转发到 backend。入口从此保持关闭直到第 9 步；不能把 502 当作正常开放状态。
3. 停止全部旧 backend/worker；验证没有旧进程、任务或数据库写连接。
4. 确认数据库最高成功版本仍为 V32，再完成并校验最终数据库备份与 MinIO 对象快照；任一恢复点不成立即中止。
5. 保留 `video-probe-temp` 卷，一次性把既有目录和工件属主迁移为 `10001:10001`；不得删卷。
6. 使用新 Compose 的 `up -d --no-deps --no-build --pull never backend` 只启动一台仍不接公开流量的新 backend，
   让 Spring 完整执行 Flyway V33–V35 与
   `IdCardBackfillFlywayCallback`；不能仅用外部 Flyway CLI 代替。
7. 核验最高版本 V35、证件号密文/HMAC、V34 保留参数、V35 历史人数与当前 2/10；从同一独立客户端再次运行
   `bash scripts/verify-public-entry-closed.sh`，证明根路径与同源 `/api/health` 仍为同一固定维护态或经授权的明确
   连接拒绝。
8. 启动除 frontend 外的其余服务，确保所有新节点使用同一镜像 digest、同一 AES key/HMAC pepper；执行健康、业务主流程、
   预签名媒体和审计检查。
9. 在 V35 生成新备份并完成 Phase 41 隔离恢复演练；全部证据归档后，最后启动新 frontend、核验 TLS/健康，
   再解除外层维护并记录 `OPEN_TRAFFIC`。任何前置失败都保持入口关闭。

## 6. 回退边界

| 时点 | 允许动作 |
|---|---|
| 新进程尚未迁移，数据库确认仍为 V32 | 按下方首版专用 Compose 中止发布并恢复 `dfdfb91` 五服务 |
| V33 已开始、尚未放流 | 禁止旧 binary 重连或 app-only rollback；优先前向修复。必须回退时，只能把 V33 前数据库与对象快照恢复到隔离替换环境，核对最高 V32 后再启动旧版 |
| V35 已放流且产生新写入 | 默认仅前向修复；全量恢复会丢失新数据，必须另行审批、停写和对账 |

MySQL DDL 非事务，不能手工删列、改 Flyway history 或只恢复数据库中的部分表来冒充回滚。任何恢复都必须同时
使用与该恢复点匹配的对象快照和密钥版本。

只有在日志与 `flyway_schema_history` 都确认 V33 **尚未开始**、数据库仍为 V32 时，才允许执行迁移前回退：

```bash
# 入口继续保持关闭；先停止可能已创建的新 frontend/backend，不删除容器或卷。
docker compose --env-file .env -p '<实际project>' \
  -f docker-compose.yml -f deploy/compose.cpu-v1.yml -f deploy/compose.existing-volumes.yml \
  stop frontend backend

# APP_IMAGE_TAG 仅对本命令临时回到 dfdfb91；使用首版自己的内部端口与 /api/health 健康合同。
APP_IMAGE_TAG=dfdfb91 docker compose --env-file .env -p '<实际project>' \
  -f deploy/rollback/dfdfb91/compose.yml \
  -f deploy/rollback/dfdfb91/compose.cpu-v1.yml \
  -f deploy/compose.existing-volumes.yml \
  up -d --no-build --pull never mysql redis minio backend

# 四个依赖/后端全部 healthy 后才启动首版 frontend；五服务 healthy 后再解除外层维护。
APP_IMAGE_TAG=dfdfb91 docker compose --env-file .env -p '<实际project>' \
  -f deploy/rollback/dfdfb91/compose.yml \
  -f deploy/rollback/dfdfb91/compose.cpu-v1.yml \
  -f deploy/compose.existing-volumes.yml \
  up -d --no-build --pull never frontend
```

以上命令要求原 `.env` 中首版仍需要的 `DOCKERHUB_NAMESPACE`、`BACKEND_PORT`、`FRONTEND_PORT` 与 MinIO
端口键仍在；第二次部署只做增量维护，不得删掉这些回退键。回退前后复算包内首版五镜像身份清单，禁止
`pull`、`down -v`、换卷或覆盖 `.env`。若 V33 已有任何开始迹象，本节命令全部禁用，只能遵循表中前向修复/完整隔离恢复边界。

## 7. 发布 GO 的最小闭环

只有以下各项同时成立，才可由独立复核者给出项目级发布结论：

- 最终 manifest/carrier/双镜像/双 SPDX/Hosted run/离线包逐字节同源；
- 新 Hosted workflow 整体成功，根与嵌套 `SHA256SUMS` exact closure；
- 隔离 V32→V35、Phase 41、Phase 00、Phase 47 与主流程证据通过；
- 目标身份预检、备份恢复点、TLS/MinIO 入口和回退演练闭环；
- 独立项目级发布复核明确 PASS；
- 用户另行明确授权实际停服、迁移、启动和切流。

功能 R5 PASS、历史 WS-7/WS-8 Hosted PASS 或本地绿色测试均不能单独替代上述发布 GO。
