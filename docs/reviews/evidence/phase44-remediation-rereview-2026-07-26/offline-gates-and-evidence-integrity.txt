## 5. PG-M4 静态反例

### 5.1 Caffeine 旧值可在补偿删除前被读取

确定性交错：

1. 旧 loader 在 epoch=0 的 miss 后持有提交前旧值。
2. `put` 读取 `before=0`，第一次比较通过。
3. afterCompletion 线程把 epoch 推进为 1，并完成底层 evict。
4. 旧 loader 执行 `delegate.put(key, STALE)`。
5. 第三线程在旧 loader 做第二次 epoch 比较前执行 `get`，直接命中 STALE。
6. 旧 loader 随后发现 epoch 已变并补偿删除。

候选测试只检查步骤 6 之后缓存为空，没有在步骤 4/5 插入第三个读者。因此“写后补删”
不能证明旧值从未被供应。

### 5.2 Redis version/payload 非原子且命中不校验 version

确定性交错：

1. 数据库事务提交。
2. afterCompletion 完成 `SET dict:items:ver:<type> <uuid>`。
3. `DEL dict:items:<type>` 尚未执行。
4. 并发 `getCachedItems` 直接 GET/反序列化旧 payload，不读取或比对 version。

若 DEL 抛错或进程在步骤 2/3 之间停止，旧 payload 与新 version 可并存到 payload 的
12 小时 TTL；读路径仍会返回旧 payload。相同 Runnable 中 Redis 异常还会跳过两个
后续 Caffeine evict，异常只在事务完成回调外层记录。

### 5.3 Redis key namespace 碰撞

- payload(`ver:foo`) = `dict:items:ver:foo`
- version(`foo`) = `dict:items:ver:foo`

后端 DTO 仅 `@NotBlank`，数据库 `VARCHAR(64)` 允许 `:`；只有前端限制
`[A-Za-z0-9_]+`。因此两个合法后端输入会共享同一 Redis key。

结论：PG-M4 未关闭。

## 6. 测试隔离合同核验

`Phase44NotificationBatchIT.insertFromSeparateConnection` 执行：

`SET SESSION innodb_lock_wait_timeout = 1`

finally 只 rollback/close，没有恢复 session variable。锁定的 HikariCP 5.1.0
`PoolBase.resetConnectionState` 字节码只恢复 JDBC readOnly、autoCommit、
transactionIsolation、catalog、networkTimeout、schema；不会恢复任意 MySQL session
variable。1205 也不会必然淘汰该物理连接。

因此后续 IT 若借到该连接，会继承 1 秒锁等待上限，形成执行顺序/连接池分配相关 flake。

## 7. 框架注释核验

锁定的 MyBatis-Plus 3.5.16 `MybatisParameterHandler.extractParameters(Map)` 会遍历
ParamMap 全部 value，以 Set 去重后逐项 `toCollection` 并执行填充。因此
`NotificationMapper` 中“加 @Param 后参数映射只剩自定义键，主键/审计填充必然失效”
的说明不准确。当前无 `@Param` + `<foreach collection='list'>` 实现本身正确。
