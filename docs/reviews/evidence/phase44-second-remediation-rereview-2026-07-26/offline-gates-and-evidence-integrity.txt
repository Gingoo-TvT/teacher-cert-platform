5. Confirmed new blocking sequence A: Redis pending ownership

Current state machine:
  begin(type)      = SET version P:<uuid> EX 60; DEL payload
  complete(type)   = SET version <normal uuid> EX 24h; DEL payload

There is one Redis value, no transaction owner set and no reference count.

Deterministic sequence:
  T1 modifies item A of type X -> begin writes P1
  T2 modifies item B of type X -> begin overwrites with P2
  T1 commits -> its afterCompletion writes normal N1 even though T2 is still active
  a reader may fill/serve the T1-only committed state under N1
  T2 physically commits -> before T2 afterCompletion, N1 payload is stale
  a process exit after physical commit but before callback can leave that stale payload
  until its 12-hour TTL

Same root:
  No forced transaction timeout was found. If one transaction remains active beyond the
  fixed 60-second pending TTL, READ_ITEMS_WITH_VERSION creates a normal version and
  reopens publishing while the write transaction is still active.

Existing Phase44 tests cover one Redis writer only. The local pending reentrancy test
proves a Caffeine counter but cannot be extended to the Redis single-value protocol.
