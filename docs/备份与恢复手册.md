# 备份与恢复手册

> 适用范围：广东技术师范大学教师能力考核平台正式上线部署。目标是保证 MySQL 业务数据、MinIO 附件/视频对象、审计与逻辑删除历史可按指定时间点恢复。
>
> **两层备份**（互补，缺一不可）：
> - **A. 应用内逻辑备份（Phase 41.2，P0-6，已落地）**：平台自带的 `DatabaseBackupService` 把恢复关键表 JDBC 逻辑导出为事务性 replace-restore `.sql.gz` 并上传 MinIO，`backup_record` 关联真实产物（大小/校验和/表数/行数）。手工触发 + 生产定时（夜间）。**这是平台自动化、可在同版本 Flyway 恢复库完整回放并核验的数据快照**。
> - **B. 运维物理备份（mysqldump 全备 + binlog + MinIO mirror）**：由运维在维护窗口/宿主 cron 执行，提供全库物理级与**时间点恢复（PITR）**能力。A 不替代 B（A 是逻辑数据快照、无 binlog PITR），B 不替代 A（A 随应用自动化、产物入对象存储、有记录审计）。

## 0. 生产凭据与栈（不再用 dev 容器/口令）

- 本手册所有命令中的账号/口令**仅 dev 栈**（`docker-compose.dev.yml`：MySQL `root/root123`、MinIO `minioadmin/minioadmin123`）示例。**生产严禁使用**。
- 生产 MySQL：应用以**非 root 最小权限账号** `teacher_app` 连接（Phase 41.1 / P0-5，`deploy/mysql-init/01-app-user.sh` 创建，`DB_USERNAME/DB_PASSWORD` 环境变量注入，3306 不对宿主发布）；**备份/恢复等运维操作用单独的运维账号**（具备 `SELECT`/`LOCK TABLES`/`RELOAD` 等，经运维保险库下发，不写入仓库、不硬编码）。
- 生产 MinIO：`accessKey/secretKey` 由环境变量注入（非 `minioadmin`），bucket 开启版本化，附件/视频禁止匿名访问。
- 应用配置（`.env`、证书/密钥）由运维加密保存，不提交仓库（仓库根 `.dockerignore` 已排除 `.env`/`.git`/`target` 等，防打进镜像层）。

## 1. 备份对象

- MySQL：`teacher_cert` 库——**应用内逻辑备份**覆盖恢复关键表（见 §7 表清单）；**运维物理备份**为全库 + binlog 连续归档。
- MinIO：`teacher-cert` bucket 对象（附件、视频、导出包）、版本与删除标记；应用内逻辑备份产物存于同 bucket 的 `db-backup/` 前缀（或独立备份桶）。
- 审计记录：`audit_log` 与 `backup_record` 只做归档和备份，不做普通管理端物理删除。

## 2. 应用内逻辑备份（自动化，Phase 41.2）

### 2.1 机制

`SystemManagementServiceImpl.triggerBackup` → `DatabaseBackupService.backup(...)`：

1. 先落 `backup_record`（`status=RUNNING`，独立事务立即提交、运行期可见）。
2. 取**单一只读连接**、`REPEATABLE_READ` 快照，对 §7 恢复关键表逐表 `SELECT *`。产物先保存会话外键设置，在**单一事务**内按清单反序 `DELETE` 37 张受管表，再正序 `INSERT` 完整快照（含逻辑删除行，`deleted` 标记原样保留），成功后 `COMMIT` 并恢复会话设置。`DELETE` 是事务性 DML；禁止改成会隐式提交的 `TRUNCATE`。
   - `flyway_schema_history` 不属于受管数据表，不会被清空或导出；schema 必须由同一发布版本的 Flyway 重建。
   - `backup_record` 只导出终态 `COMPLETED/FAILED`。本次任务以及任何并发任务的 `RUNNING/PENDING` 均排除，避免灾备后遗留永久假运行记录；此前已完成/失败的历史记录仍在快照中。由于本次任务自己的最终记录不在其产物内，对象同时以 MinIO user metadata 保存 `record-id/sha256/restore-mode/table-count/row-count`，灾备清单不得只依赖源数据库。
   - 文本值以 UTF-8 十六进制表达式输出，避免 SQL mode、引号、反斜杠或换行改变回放语义；备份类型/范围只以单行安全注释写入。
3. `putObject` 上传到 MinIO：默认 `teacher-cert` 桶的 `db-backup/` 前缀，对象名 `teacher_cert_<yyyyMMdd_HHmmss>_<recordId>.sql.gz`；对象 user metadata 同步保存产物索引和 SHA-256，供源库不可用时核验。
4. 回写 `backup_record`：`status=COMPLETED`、`storage_uri=minio://<bucket>/<objectKey>`、`byte_size`（gzip 字节数）、`checksum=sha256:<hex>`、`table_count`、`row_count`、`finished_at`。**任一步失败** → `status=FAILED` + `error_message`（记录留痕、绝不伪造 COMPLETED）。

产物是**真实、非空、可解压、可完整替换回放**的逻辑数据快照（不是“演练记录占位”，也不是会保留快照外行的 UPSERT/REPLACE 合并脚本）。

### 2.2 手工触发

```bash
# test_sys_admin 需权限 system:backup；备份类型 mysql/minio/full 任填（当前实现导出逻辑数据）
curl -sS -X POST http://<host>/api/system/backup/trigger \
  -H "Authorization: Bearer <token>" -H "Content-Type: application/json" \
  -d '{"backupType":"full","scope":"manual","remark":"上线前手工全量"}'
# 返回 data.storageUri / byteSize / checksum / tableCount / rowCount
```

查询记录：`GET /api/system/backup`（`system:backup`），或 `SELECT id,status,storage_uri,byte_size,checksum,table_count,row_count,started_at,finished_at FROM backup_record ORDER BY id DESC LIMIT 10;`

### 2.3 生产定时备份（默认关闭，仅 prod 开启）

- `BackupScheduleConfig`（`@EnableScheduling` + `@Scheduled`）由 `platform.backup.schedule.enabled` **门禁，默认 `false`**——dev/测试/未配置环境**不注册、不触发**（不扰动 IT）。
- `application-prod.yml` 显式开启：

```yaml
platform:
  backup:
    schedule:
      enabled: true
      cron: "0 0 3 * * *"   # 每日 03:00 低峰全量
    prefix: db-backup/
    # bucket: teacher-cert-backup   # 可选：独立备份桶（不设则复用 minio.bucket）
```

- 保留策略：MinIO 侧对 `db-backup/` 前缀配生命周期规则（如保留 30 天），或运维定期 `mc rm` 过期对象；`backup_record` 只增不删（审计归档）。

### 2.4 从应用产物恢复

```bash
# 1) 从 MinIO 取产物（key 见 backup_record.storage_uri）
mc alias set tminio http://<minio-host>:9000 <ACCESS_KEY> <SECRET_KEY>
mc cp tminio/teacher-cert/db-backup/teacher_cert_YYYYMMDD_HHMMSS_<id>.sql.gz ./
# 2) 校验完整性（与 backup_record.checksum 比对）
sha256sum teacher_cert_YYYYMMDD_HHMMSS_<id>.sql.gz   # 应等于记录里 sha256: 之后的值
# 3) 创建“专用隔离恢复 schema”，用与产物相同的发布版本只执行生产 Flyway migrations。
#    迁移后 RBAC/字典/参数种子存在是正常且必须覆盖的场景；不要加载 db/testseed/demo。
# 4) 确认没有应用连接该恢复 schema 后，完整回放；禁止加 mysql --force。
set -o pipefail
gunzip -c teacher_cert_YYYYMMDD_HHMMSS_<id>.sql.gz \
  | mysql --binary-mode -u<ops_user> -p teacher_cert_restore
# 5) 核对 37/37 表的行数与确定性内容指纹、逻辑删除行、关键父子关系，
#    并确认 flyway_schema_history 仍是产物对应版本；全部通过后才允许在维护窗口切换。
```

> **恢复红线**：
> - 产物不含建表 DDL，必须先由**同一发布版本**的生产 Flyway migrations 建好专用恢复 schema；所谓“新恢复库”在迁移后会含生产种子，并非数据为空。
> - 脚本会在单一事务内删除并替换 37 张受管表，**严禁直接回放到正在服务的生产 schema**，严禁使用 `--force` 忽略错误。任一语句失败应让连接退出并回滚整次替换。
> - 先在隔离库完成整表核验，再按变更窗口切换；需要**指定时间点恢复**时使用 §3–§5 的物理全备 + binlog。
> - 自动化 IT 使用 JDBC 会话验证事务回滚语义；上述真实 `mysql` 客户端管道、生产切换与凭据路径仍须由独立运维在隔离环境演练，不得把 IT 结果表述为生产恢复已演练。

## 3. MySQL 物理全备（运维）

> **证据边界**：§3–§5 是待独立运维落地并演练的灾备方案，不属于 Phase 41 应用自动化 IT 的已验证范围。仓库当前未提供 binlog 异机连续归档作业，也未证明生产实例的 `log_bin/server_id` 实际配置；未完成坐标、归档、隔离恢复实例和回放演练前，禁止宣称 PITR 已闭环。

推荐每日低峰期执行一次全备，备份文件按日期保存。生产用运维账号（非 root、非 `teacher_app`），口令经运维保险库下发。`--source-data=2` 将与一致性快照对应的 binlog 文件和位置以注释写入产物，作为后续增量回放起点。

```bash
mysqldump -h<host> -u<ops_user> -p --single-transaction --source-data=2 --routines --triggers --events --set-gtid-purged=OFF teacher_cert > backups/mysql/teacher_cert_YYYYMMDD.sql
grep -n "Dump completed" backups/mysql/teacher_cert_YYYYMMDD.sql   # 校验
grep -n "CHANGE REPLICATION SOURCE TO" backups/mysql/teacher_cert_YYYYMMDD.sql   # 记录回放起点
```

保留策略：每日备份保留 14 天，每周备份保留 8 周，每月备份保留 12 个月。生产环境需将备份同步到异机或对象存储。

## 4. Binlog 归档（运维，PITR 前提）

生产 MySQL 必须开启 binlog，并保证 `server_id` 唯一；还必须建立持续复制、完整性校验、异机保存与过期告警。下列仅为配置基线，运维须对实际实例执行只读核验后留证：

```ini
log_bin=mysql-bin
binlog_format=ROW
binlog_expire_logs_seconds=1209600   # 14 天（MySQL 8：expire_logs_days 已弃用）
```

每日归档 binlog：`mysqladmin -h<host> -u<ops_user> -p flush-logs`，将最新 `mysql-bin.*` 复制到 `backups/binlog/` 或异机目录。

## 5. MySQL 时间点恢复（运维）

恢复演练必须使用与生产网络和存储隔离的 MySQL 实例；在隔离实例内沿用源库名 `teacher_cert`，避免误以为给 `mysql` 客户端传默认库就会改写 binlog 事件中的原库名。真实灾备命令只由获授权的运维人员执行。

1. 从全备注释读取 `SOURCE_LOG_FILE/SOURCE_LOG_POS`，确认归档文件从该坐标起连续、校验和正确。
2. 在隔离恢复实例创建 `teacher_cert`，恢复最近一次全备。
3. 从记录的文件/位置起，按完整文件序列回放到目标时间；先输出到受控临时文件审阅，再输入隔离实例。不得从固定的 `mysql-bin.000001` 猜起点。
4. 全量核对关键表和业务不变量，并验证目标时间边界；保留执行人、命令版本、坐标和校验值。
5. 独立审批通过后，才制定生产维护窗口内的切换方案。**禁止把 binlog 直接管道到在线生产实例，也禁止在未校验前覆盖生产库。**

## 6. MinIO 备份与恢复

生产 bucket 必须开启版本化，附件与视频禁止公开匿名访问。凭据用生产 `accessKey/secretKey`（非 `minioadmin`）。

```bash
mc alias set tminio http://<minio-host>:9000 <ACCESS_KEY> <SECRET_KEY>
mc version enable tminio/teacher-cert
mc mirror --overwrite --preserve tminio/teacher-cert backups/minio/teacher-cert   # 备份（含 db-backup/ 逻辑产物）
mc mirror --overwrite --preserve backups/minio/teacher-cert tminio/teacher-cert   # 恢复
```

恢复后用业务接口或数据库 `file_object` 抽查对象 key 是否可生成限时预签名，确认材料、视频、导出包与 `db-backup/` 逻辑产物均可访问。

## 7. 应用内逻辑备份的表清单（恢复关键表，curated）

`DatabaseBackupService.BACKUP_TABLES`（显式枚举、稳定有序；**刻意不含** Flyway 的 `flyway_schema_history`——schema 由迁移在恢复库重建）：

- 参考/组织/字典：`sys_region`、`sys_dict_type`、`sys_dict_item`、`teaching_subject`、`sys_college`、`sys_major`、`training_goal_config`、`major_training_goal`
- RBAC/用户/数据范围/评审组：`sys_permission`、`sys_role`、`sys_role_permission`、`sys_user`、`sys_user_role`、`sys_user_data_scope`、`reviewer_group`、`reviewer_group_member`
- 参数/审计/通知/备份记录：`sys_param`、`audit_log`、`notification`、`backup_record`
- 业务域：`student`、`training_profile`、`process_material`、`exemption_request`、`exemption_material`、`video_review`、`video_review_task`、`video_upload_session`、`video_upload_chunk`、`video_finalization_object_candidate`、`ability_test_result`、`certificate`、`cert_sequence`、`import_export_batch`、`import_record_ref`、`import_error_detail`、`file_object`

新增业务表须同步加入本清单（否则不会进逻辑备份）。物理全备（§3）无此限制、覆盖全库。

两层自动证据各守边界：

- `Ws03CandidateBackupRestoreIT` 校验 37 个 section 与 schema 表集合一致，并逐字段回放 `video_finalization_object_candidate` 后继续执行真实对账；对象删除由安全内存替身承接。
- `Phase41BackupIT` 使用两个唯一前缀的任务专属 scratch schema：source 与 restore 均只加载生产 migrations；restore 在确认 Flyway 种子存在后完整执行真实 gzip，逐表比较 37/37 行数与全字段 SHA-256 指纹、软删/特殊文本/父子关系、快照外行移除、历史终态备份保留、并发非终态备份排除和 `flyway_schema_history` 保留；同一产物二次回放保持精确一致，并通过测试内 JDBC 会话验证中途 INSERT 失败会回滚前置 DELETE。真实 `mysql` 客户端回放仍属于独立运维演练。

## 8. 业务逻辑删除恢复

业务表均使用 `deleted` 逻辑删除，逻辑备份**原样保留** `deleted` 标记。误删优先走业务恢复或受控 SQL 更正，操作必须留痕：

- 记录恢复原因、操作人、时间、目标表与主键。
- 恢复前备份被恢复行。
- 恢复后查询 `audit_log` 确认更正动作有审计。

## 9. `backup_record` 字段

| 字段 | 含义 |
|---|---|
| `backup_type` | 备份类型 `mysql`/`minio`/`full`（当前实现导出逻辑数据，类型用于分类） |
| `status` | `RUNNING`→`COMPLETED` / `FAILED`（真实状态流，非固定 COMPLETED） |
| `scope` | 触发范围（`manual`/`scheduled`/演练备注） |
| `storage_uri` | `minio://<bucket>/db-backup/...sql.gz`（真实产物位置） |
| `byte_size` | 产物字节数（gzip 后） |
| `checksum` | `sha256:<hex>`（与产物比对完整性） |
| `table_count`/`row_count` | 导出表数/行数 |
| `started_at`/`finished_at`/`operator_id`/`error_message` | 起止时间/操作人/失败原因 |

## 10. 上线演练清单

- 手工触发一次 `POST /api/system/backup/trigger`，确认返回 `COMPLETED` + 非空 `byteSize`/`checksum`/`rowCount`，并从 MinIO 取回产物 `sha256sum` 与记录一致、`gunzip` 后含真实 `INSERT` 行。
- 将该产物回放到同版本 Flyway 已迁移的专用 `teacher_cert_restore` schema（迁移种子必须存在），禁止 `--force`；核对 37/37 表行数与内容指纹、逻辑删除行、关键父子关系和 `flyway_schema_history`，而非只抽查少数表。
- 用同一产物重复回放一次，结果必须完全一致；构造一次隔离库内中途失败，确认整次 DELETE + INSERT 原子回滚。
- 演练物理全备 + binlog PITR（§3–§5），确认可恢复到指定时间点。
- 演练 MinIO `mc mirror` 往返，确认附件/视频与 `db-backup/` 产物均可恢复。
- 记录演练日期、执行人、产物编号（`backup_record.id`）、校验结论。
